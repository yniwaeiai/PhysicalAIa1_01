## 1. 人間デモの手首姿勢の解析（計画の前提の検証）
### 1.1 方法と最初の結果
- 対象: LIBERO 原本 hdf5（各 50 デモ）。`kadai/scripts/analyze_wrist_tilt.py`。手先姿勢は `obs/ee_ori`（軸角）から回転行列にし、ツール z 軸の鉛直下向きからの傾き `tilt`、水平成分の方位 `az`、グリッパを閉じる指令（`actions[:,6]` が −1→+1）の瞬間の姿勢・位置を算出。
- 結果: 引き出し＋ボウル、K3、K4、電子レンジでは閉じる瞬間が取れたが、**中段引き出しと皿押しでは閉じる指令が 1 回も無かった**（`cmd values {-1.0}`）。
- 解釈の更新: 人間は引き出しを**グリッパを開いたまま引っかけて**開けている。「閉じる瞬間」を接触の代理にする設計は誤り。また「引き出し＋ボウル」の最初の閉じる動作はボウル把持で、引き出しの接触ではない。

### 1.2 接触区間の定義への切り替え
- 判断: 操作対象（可動関節または皿の自由関節）の変位が出る区間を接触区間と定義。`out` 窓 = 変位が最大の 5% を超えた時点 → 90% に達した時点。固定物（棚・電子レンジ・コンロ）の座標系で姿勢を表現。`kadai/scripts/analyze_contact_windows.py`、出力 `kadai/state/contact_windows_*.{json,csv}`。
- 実装上の確認事項: `states` は `[time, qpos(nq), qvel(nv)]`（中段引き出しの環境で 1+41+37=79）。関節名は robosuite のラッパ `m.joint_id2name(j)` で取得（`mujoco.mj_id2name` は直接使えない）。

### 1.3 結果（out 窓の tilt 中央値）
| 基底 | tilt | 備考 |
|---|---|---|
| 中段引き出しを開ける | 61.6°（p10–p90: 51–77） | 方位は全デモで同じ（集中度 0.99）、グリッパ開 |
| K4 下段引き出し | 28.2°（12–38） | 後に「閉める押し」と判明（§1.5） |
| K6 電子レンジ | 19.9°（13–42） | 「閉める」 |
| 上段引き出し＋ボウル | 3.7° | 人間も真下向き |

| K3 つまみ | 5.2° | 同上 |
- **計画の前提が崩れた:** 「3 動作は傾けないと実行できない」は、上段引き出し・皿押し・つまみには当てはまらない。コンペ側の expert の失敗原因は傾きでなく別（取っ手の検出・棚との干渉）の可能性が高い（**未検証**）。
- 判断（ユーザと合意）: 焦点を傾きが効く 3 基底（中段引き出し、K4、電子レンジ）に絞る。成功の線を「3 基底それぞれで 成功 ∧ 衝突なし ≥ 70%」に変更。コンペへの還元条件（10/18 に 4 基底）は外した。

### 1.4 傾きの向きの確認と「y 鏡映」仮説の棄却
- 事実: 中段引き出しは世界 +y 方向へ開く。引き始めのツール z 軸 = (−0.06, −0.85, −0.53)、引き終わり (−0.06, −0.96, −0.27)。指先は引く向きと逆（棚の内側）にほぼ水平。指の開閉軸は取っ手の棒に沿う。
- 検証したこと: 過去のコンペ側記録に「デモ記録の ee_pos は現行の world と y 鏡映」とあったため、hdf5 の `obs/ee_pos`・`obs/ee_ori` と、`states` を sim に流して再計算した手先を比較。**一致**（例: t=105 で sim (−0.004, −0.135, 1.032)、hdf5 (−0.004, −0.131, 1.033)）。鏡映の問題は本データでは無い（LeRobot v3 の話であり、原本 hdf5 は対象外）。

### 1.5 訂正: K4 の引き出しは最初から開いている
- 事実: K4 人間デモの下段引き出し関節は始値 q = −0.14〜−0.16（開）→ 終値 0.002（閉）。
- 誤り: 窓の定義が |Δq|（変位の大きさ）で向きを区別していなかったため、閉める押しの区間を「開ける」と読み、計画書にも「下段を開ける」と書いた。
- 対処: 結果文書と計画書を訂正（コミット `d5c1d75` 直後の訂正コミット）。電子レンジと K4 は同系統（傾けて押して閉める）、中段引き出し（引っかけて開ける）は別系統と整理。
- 教訓: 窓の定義に向き（符号）を入れる。始値・終値を先に見る。

## 3. 中段引き出し「傾けて引っかけて引く」expert の開発
### 3.1 設計
- 既存の `scripts/t2_primitives.py` の `Seg`/`SegRunner` は姿勢目標が「世界 z まわりの回転」だけで、手首を傾けられない。→ 全姿勢（クォータニオン）を目標にできる `HookRunner` を新規に書いた（`kadai/scripts/run_drawer_hook.py`）。OSC_POSE の規約（位置 [-1,1]×0.05 m、回転 [-1,1]×0.5 rad の世界軸角、グリッパ −1 = 開）。
- 目標の作り方: 人間デモ 50 本の接触時点（onset 基準のオフセット −60…peak）の手先位置の中央値と姿勢の回転平均を、棚座標で保存（`kadai/state/hook_keyposes_middle.json`。引っかけ位置の標準偏差 1.7/0.9/0.5 cm、姿勢のばらつき約 11°）。実行時の棚の位置・向きで世界座標へ直して追従。

### 3.2 失敗と原因分析（v0 → v1）
- 初回: 0/4 成功。引き出しの変位 q ≈ 0（取っ手に掛かっていない）。
- 仮説と検証（因果を主張する前に別仮説を挙げる規律に従った）:
  - 仮説 A「デモ座標が鏡映している」→ §1.4 で棄却。
  - 仮説 B「指の開き・グリッパ状態が違う」→ 開（−1）で人間と同じ。
  - 仮説 C「到達位置が人間より約 1.5 cm 浅く 1.3 cm 高い」→ 指の本体の位置を棚座標で比べて確認（自分: z 0.163/y −0.151、人間: z 0.150/y −0.132）。接触が全く無い（`contacts=[]`）ことと整合。
- 決め手: 人間デモの接触を力つきで調べた。**指のパッドが取っ手の棒（`g29`）の上面の奥側の縁に乗り、法線力約 200 N で押しつけて引く**。棒は水平で棚の x 方向、standoff（`g30/g31`）は x=−0.036/+0.029。取っ手の geom 名に `handle` は無い（無名 `g21`〜`g31`）。当初は前板（`g22/g24`）との接触に見えたが、引き出しが動いた後の状態（q=−0.046）で測ったため座標が 4.6 cm ずれており、静止位置に直すと棒の奥側上縁だった。
- 対処: キーポーズの高さに補正 `dz` と奥行き補正 `dy` を入れて掃引（3×3、各 4 seed）。**`dz=0` だけ全滅（0/4）、`dz` ≤ −0.012 は 4/4**（`dy` は 0〜3 cm で影響なし）。成功域の中央 `dz=−0.018` を既定に（12 seed すべて 12/12 を `dz`∈{−0.012, −0.018, −0.024} で確認）。
- 解釈: 人間デモの手先中央値の「高さ」は、棒の上に指を乗せる位置として約 1.5 cm 高い。ロボットの OSC 追従の定常誤差や、キーポーズが onset 前の中央値であることが一因の可能性（未検証）。

### 3.3 評価（v1）と限界の発見
- LIBERO-Plus の init 50 行で 成功 ∧ 対象外 ≤ 1 mm = **50/50**、T = 165〜166（ほぼ同一）。コミット済み（`kadai/state/drawer_hook_v1_seeds0-49.json`）。
- 限界: **T がほぼ同一 = init 行は棚もロボット姿勢も変えていない**。「50/50」は汎化の証拠として弱い、と自己判断。摂動の追加へ。

### 3.4 摂動試験の追加と高速化
- 追加: `--robot-noise`（初期 7 関節に ±x rad）、`--cab-shift`（棚の xy ±x m）、`--cab-yaw`（棚の向き ±x deg）。
- 当初結果: ロボットノイズ ±0.1 rad・棚 ±3 cm/±5°・両方、強い版 ±0.2 rad/±6 cm/±10° のすべてで 12/12。
- 効率の発見: 全 seed で `H_IN` が `timeout`（上限 70 step まで粘る）。許容 0.8 cm/8° → 1.5 cm/12° に緩めると、摂動下で 12/12 のまま **T の中央値 166 → 111.5（人間デモ中央値 136.5）**。許容 2 cm/15° でも 110。既定を 1.5 cm/12° に。

### 3.5 バグの発見と修正（摂動が効いていなかった可能性）
- 発見の経緯: K4 用の同型ハーネス（`run_close_push.py`）で `AttributeError: 'MjSim' object has no attribute 'data'` が出て、**`env.reset()` のたびに sim オブジェクトが作り直される**ことに気づいた。
- 影響: 中段引き出しのハーネスでは、棚の摂動を「リセット前に取得した古いモデル」に書いていた。つまり §3.4 の**棚のずれ・回転は実際には効いていなかった**（ロボット姿勢ノイズだけが有効）。「摂動で T が 165〜173 にばらつく」という操作チェックは、ロボットノイズによるもので、棚摂動の有効性の証拠になっていなかった。
- 対処: sim/model を毎エピソード reset 後に取り直し、基準値は初回に保存して絶対値で摂動を与える形に修正。操作チェックを追加して、棚の世界位置・向きが seed ごとに実際に変わること（位置が約 ±6 cm、yaw が 180° 付近で ±10° 程度）を確認。
- 再試験（修正後）: 棚のみ（±3 cm/±5°）12/12、ロボット+棚（±0.1 rad/±3 cm/±5°）12/12。
- **強い摂動（±0.2 rad / ±6 cm / ±10°、修正後）は 8/12（引き出しが開いた done は 10/12）。** 修正前の「12/12」は棚の摂動が入っていなかったための過大評価だった。失敗 4 件:
  - seed 2・7: 引き出しは開いたが、対象外の物体が 1.87 mm・2.67 mm 動いた（衝突。成功の線 ≤ 1 mm に抵触）。
  - seed 5・9: 引っかけ区間 `H_HOOK` が timeout し、引き出しが開かなかった（q=0.002）。seed 9 は `H_IN` も timeout。
  - 機構は未分析（次に seed 2/7/5/9 で接触と棚の姿勢を調べる）。基準の摂動（±0.1 rad/±3 cm/±5°）では 12/12 で、強い摂動で初めて露出する限界。
- 教訓: 操作チェックは「独立変数そのもの」を直接測る（T のばらつきでなく、棚の位置）。

## 4. K4 下段引き出し「傾けて押して閉める」expert の開発（進行中）
- 人間デモの解析（`extract_close_keyposes.py` → `kadai/state/close_keyposes_k4_bowl_drawer.json`）: 押す窓は中央値 28.5 step。接触の集計は、手の本体・finger1 が下段の取っ手（`g40`）を押し、finger2 が `g33`、link5 が棚の天板（`g9`）に当たる。個別デモ（demo_0）: 指は開いたまま、手先は棚座標で y −0.23 → −0.14 を z ≈ 0.06 で移動、ツール z 軸 (−0.15…−0.25, 0.47, −0.87)（約 30° 前傾で指先が押す向き）。別デモ（demo_3）は傾き 0° → 38° へ押しながら増やし、z は 0.05 → 0.012 まで下がる。**人間は一定姿勢ではなく、押しながら姿勢を変えている**（人間間のばらつきも大きく、onset 時点の姿勢の回転ばらつき 19°）。
- 単独試験ハーネス `run_close_push.py`（引き出しだけ、ボウル無し、成功 = q > −0.004 ∧ 対象外 ≤ 1 mm）。初回（onset+8 のキーポーズ姿勢を固定、手先 z=0.05、y: −0.30 → −0.06）: 4 seed とも **q = −0.15 → −0.018 で停止**（閉じ切りまで 1.8 cm 不足、C_PUSH が timeout）。
- 原因分析: 停止時の接触を力つきで測定 → 手の本体（`gripper0_hand`）が中段の取っ手（`g29`、z=0.102）に 30 N、finger1 が下段の取っ手（`g40`）に 26 N。手先は y=−0.122 で動かない。コンペ側の記録（K4 で「0° は手の本体が上の段の取っ手に当たる」）と同じ機構。人間は押す途中で傾けて回避している。
- 対処: 押す姿勢に追加の前傾（棚の x 軸まわり 0/15/30/45°、正 = 指先が押す向きへ倒れる）と手先高さ（0.05/0.042）を掃引（各 2 seed）。
  | 追加前傾 | 結果 |
  |---|---|
  | 0° | q が閉じ切らない（−0.007〜−0.017）または閉じてもワインボトルに 1.3 mm |
  | 15° | 4/4 閉まる、z=0.05 の seed 0 だけボトル 0.89 mm |
  | 30° | 4/4 閉まる・衝突なし |
  | 45° | 閉まり切らない（q −0.03〜−0.07） |
  動作域 15〜30° の中央の +22°、z=0.046 を既定に。
- **試験設定の誤り（2 件）と訂正:**
  1. 初回の 12 seed 評価（ボウルを机上の元位置のまま）で「成功 ∧ 衝突なし」が 4/12・6/12・5/12。閉まる動作自体は 12/12。失敗は他物体の移動。実タスクではこの時点でボウルは引き出しの中にあり、試験が実タスクを反映していない。
  2. ボウルを人間デモ終端の位置（棚座標、`kadai/state/k4_bowl_in_drawer_cabinet_frame.json`）へ置いたところ、引き出しが閉まらなくなった（q −0.084〜−0.095）。原因は、その位置が**引き出しが閉じた状態**の座標なのに、試験開始時は引き出しが開いている（q≈−0.15）ため、ボウルが棚の本体に食い込んでいたこと。ボウルの置き位置に引き出しの現在変位を足して修正。
  また、ボウルはこのタスクの対象物（OOI）で、引き出しに連れて動くのは正常なので、衝突判定から除外した（判定は本番と同じく対象外物体のみ）。
- 修正後の基準条件（12 seed）: 閉まる 12/12、成功 ∧ 衝突なし 8/12。失敗 4 件（seed 7, 9, 10, 11）は**全て開始直後（C_PRE、t=8〜9）に finger2 がワインボトルに接触**（移動 8〜74 mm）。初期姿勢から押す位置へ最短で動く経路上にボトルがあるため。対処: 経路の高さを上げる（`zpre` 0.15 → 0.30 m）。**修正後 12/12（成功 ∧ 衝突なし）**。
- **摂動試験（24 seed、zpre=0.30、ボウルは引き出しの中）:**
  | 水準 | 閉まる | 成功 ∧ 衝突なし | 失敗の内訳 |
  |---|---|---|---|
  | 中（ロボット ±0.1 rad、棚 ±3 cm/±5°） | 24/24 | **22/24** | seed 4: 押し中（t=82）にボトルを 56.5 mm、seed 19: 開始 t=1 にボトル 3.07 mm |
  | 強（±0.2 rad、±6 cm/±10°） | 21/24 | **17/24** | 開始 t=1 のボトル接触 2 件（seed 4: 3592 mm = 弾き飛ばし、seed 5: 2.38 mm）、押し中（t=77〜98）のボトル接触 3 件（約 56 mm が 3 件、103.8 mm が 1 件）、閉まらない 3 件（seed 9: q 変化なし、14: q −0.006、19: q −0.056） |

## 5. K6 電子レンジ「傾けて押して閉める」expert（`run_micro_close.py`）
- 解析（`extract_close_keyposes.py microwave_k6`、扉座標系の確認）: 扉の関節は z 軸まわり（範囲 −2.094〜0、閉 = q > −0.005）。扉の板は扉座標で x 0〜0.259（ヒンジからの径方向）、y −0.025〜−0.001 の薄板。**人間の手先は棚の座標では位置のばらつきが大きい（標準偏差 最大 12 cm、姿勢のばらつき 34〜40°）が、扉の座標に直すと押す点が安定**（x≈0.09–0.13、y≈−0.06〜−0.11、z≈0.05）。接触はパッド（finger1/2_pad）と扉板（`g17`）。板の −y 側から +y 方向（閉じる向き = ẑ×r）へ押す。
- 設計: 目標を「扉の座標系の固定点」にして扉の動きに追従（弧に沿って進む）、押し込み量は板の面（y=−0.025）+ depth 0.02 m。姿勢は人間デモの onset+8 の電子レンジ座標の姿勢を固定。区間: M_PRE（扉の点の上 +0.10）→ M_LOW → M_PUSH（q > −0.005 で完了）。`HookRunner` に `world_pos`（動く物体に追従する目標）を追加。
- 結果（マグは扱わない単独試験。マグは対象物として衝突判定から除外）: 基準（12 seed）**12/12**、中（24 seed、±0.1 rad/±3 cm/±5°）**24/24**、強（±0.2 rad/±6 cm/±10°）**23/24**（失敗 1 件: seed 3、押しが timeout で q −0.453 止まり、対象外の接触なし）。ステップ数は 47〜53（人間の窓の中央値 26.5。人間デモ全体は 242〜284 だがマグの配置を含む）。初回の試行で成功しており、パラメータ調整はしていない。
- 留意: 初回から成功した点は、押す点の座標系を扉に取った設計（K4 の固定の棚座標では押す途中で姿勢が合わなかった）が効いたと考えられるが、K4 と電子レンジは別の機構（直線 vs 弧）なので因果は主張しない。

## 14. 推論時の摂動（停留対策）の試験 — 結果の前に固定した設計（10/13 19:00 JST）
- 発端（ユーザ提案）: フローマッチングの方策では、停留（ためらい・同じ観測で同じ行動を繰り返して止まる）への対策として、摂動を加えると性能が上がることがある。今回のタスクで有効かは不明なので試す。動機となる失敗例: 中段引き出しの基準線の例 2（引き出しの前でためらう）と、K6 例 3（扉の近くで止まる）。
- 実装（`eval_kadai_closedloop.py`、既定は無効）:
  - `--act-noise σ`: 実行する行動の位置・回転 6 成分に N(0, σ) を毎 step 足す（正規化行動の単位。位置 1.0 = 5 cm/step）。
  - `--stall-kick`: 窓 20 step の手先の移動量が 2 cm 未満で、かつ step ≥ 30 のとき停留と見なし、8 step のあいだ位置に一定の乱れ（ランダム方向、大きさ 0.2 ≈ 1 cm/step）と回転ノイズを足し、行動計画を捨てて再推論させる（冷却 40 step）。
  - ★別案（未実装）: フローマッチングの初期ノイズのスケーリング（サーバ側。`Policy.infer(obs, noise=...)` は対応しているが websocket サーバが渡していない）。今回の結果が有望なら次に試す。
- 対象モデル: LoRA 最終（2400 step）。条件: 各タスク 48 本、seed 1000–1047（最終モデルの無摂動評価と同じ seed・同じ環境の摂動）、条件間は同じ方策サーバを共有。
  | 条件 | 内容 |
  |---|---|
  | N0 | 無摂動（最終評価そのもの） |
  | N0b | 無摂動の再実行（**ノイズ床**。同じ設定を 2 回測った差） |
  | A05 | 行動ノイズ σ=0.05 |
  | A15 | 行動ノイズ σ=0.15 |
  | K | 停留トリガー（kick） |
- ★操作チェック（独立変数が本当に動いたか）: `act_dev`（実際に加わった摂動量の平均）は A05≈0.04、A15≈0.12（E|N|=0.8σ、クリップ分は少し減る）、N0・N0b・K では 0 に近いこと（K は kick の間だけ）。`n_kicks` は K 条件でのみ 0 超、N0 系は 0。満たさなければ測定を無効とする。
- 予測（結果を見る前の私の見立て。外れたらそれ自体が知見）:
  - P1: K は、停留型の失敗（中段引き出しの A 型）を持つタスクで成功率を上げる（中段引き出しで +4 pt 以上）。K6 は元の成功率が高いので差は出にくい。
  - P2: A05 はノイズ床の内側（効果なし）。A15 は精度が要る中段引き出し（成功の回廊が約 1 cm）で成功率を**下げる**（−5 pt 以上）。
  - P3: ノイズ床は、n=48 で二項分布の標準誤差 約 7 pt なので、条件差が約 ±10 pt 未満は区別できない。
- 採否の基準: ある摂動を「有効」と呼ぶのは、(a) あるタスクで成功率が N0 に対して +10 pt 以上（ノイズ床の約 1.5 倍）上がり、(b) 衝突なしの率が 5 pt を超えて下がらず、(c) ステップ数の中央値が 20% を超えて増えないとき。それ以外は「効果を検出できない」と書き、有効・無効の断定はしない。n=48 では小さな効果は見えない。

## 16. 摂動試験の最初の起動の失敗（約 35 分の無駄）と、その分析・対処（10/13 19:15–20:00 JST）
- 事象: 摂動 4 条件 + K6 の収集を並列起動（10:14 UTC）→ 35 分後（10:49）にほぼ結果ゼロ（全条件でエピソード数 0〜1）、方策サーバは `Killed`、`VARIANTS_ALL_DONE` が出ていた。
- 原因（2 件、どちらも私の実装不備）:
  1. **待機条件のバグ**: 共有サーバを使う `REUSE_SERVER` モードで、`pod_run_eval.sh` が待つ対象のログ `serve_<条件名>.log` は、サーバを起動しないモードでは**存在しない**。各条件が起動判定の上限（5 秒 × 240 = 20 分）まで待ってからクライアントを起動した（ログに「server up after ~1200s」）。「プロセスが待っている」ことを正常と見なしていた。
  2. **コードのバグ**: 摂動を足すために `act[:6] = ...` と代入したが、サーバから届く配列は読み取り専用で `ValueError: assignment destination is read-only`。全クライアントがリトライの 3 回を使い切って落ちた。
  - 方策サーバが `Killed` になった原因は未特定（`dmesg`・cgroup のログが見えない）。`run_variants.sh` が `wait` で全バックグラウンド（サーバ含む）を待っていたため、サーバの終了で初めて `VARIANTS_ALL_DONE` が出た、という副次的な設計不備もあった。
- 根本の失敗: **大きな評価を投げる前に、1 エピソードの煙検査をしなかった**（実験設計の規律「操作チェックを先に」を飛ばした）。
- 対処: (a) コピーを取る（`np.array`）、(b) REUSE モードは `SERVER_LOG` を待ち、上限内に起動メッセージが無ければ `SERVER_NOT_UP` で即終了、(c) サーバを単独の常駐スクリプトに分離（他ジョブの `wait` に縛られない）、(d) **煙検査を先に行い、操作チェックを確認してから本番**: ノイズ σ=0.15 の 1 エピソードで `act_dev` = 0.1198（期待値 0.8×0.15 = 0.12 ✓）、強制キック（停留距離 5.0 m）で `n_kicks` = 6・`act_dev` = 0.018（キック中のみ）✓。(e) 並列度を抑えた（4 条件 × 3 タスク × 4 シャード + K6 の 16 = 64 クライアント）。
- 損失: 約 35 分（GPU はサーバ起動後ほぼ遊休、約 $0.6）。ただし学習済みモデルと評価データは無事。
- 教訓（再発防止）: (1) 待機ループの条件は「結果（起動メッセージ・進捗）」で判定し、判定対象が存在するかも確認する。(2) 新しいオプションは必ず 1 エピソードで通してから並列に投げる。(3) 長時間ジョブは、起動後 2〜3 分で**進捗（エピソード数）が増えているか**を必ず見る。

### 17.3 第 2 弾の設計（結果の前に固定、10/13 20:40 JST）
- 動機: ユーザ提案の「フローマッチングの停留対策としての摂動」は、行動ノイズ・手先ベースのキックでは効果なし。フローマッチングに固有の摂動として、**初期ノイズのスケーリング**を試す（`serve_policy_noise.py`: `obs["_noise_scale"]=τ` で x0 = τ·N(0,I)。openpi の `Policy.infer(obs, noise=...)` を利用、ソースは無改変）。停留検出は**タスク進捗ベース**（タスク関節 q が窓 30 step で 0.004 未満しか動かない、step ≥ 60）に改める。

### 18.4 結論と次の方針（暫定）
- ユーザ提案の「停留対策としての摂動」は、**行動ノイズ・手先ベースの停留キック・初期ノイズのスケーリング・q 停留からの再サンプリングのいずれでも、全体の成功率を検出可能な大きさでは上げなかった。** 行動ノイズは精度が要る中段引き出しでは有害だった。ただし、(a) 検出器が局面を知らない（誤発動）、(b) 標的 seed の n が小さい、(c) F10 の対照で小さな差が出ている、という限界があり、「効かない」ではなく「この実装・この規模では効果を検出できなかった」と書く。
- より重要な知見は**失敗の構成**: 運（約 3 分の 1）、決定的（約 3 分の 1、強い摂動に集中）、中間。→ 決定的な失敗は**学習分布の端**（強い摂動は学習データの 25%）の問題で、摂動で救えない。データ側の対処（強い摂動の expert データの追加、復帰データ）が有望。
- 運の失敗には、推論側の対処が原理的に効くはず（同じ初期条件で別のサンプルなら成功する）。例: 「ゴール到達の検証つき再試行」（成功しなければ別ノイズで引き直す）や best-of-N。ただしゴール判定の特権情報が要るので、本課題の枠では慎重に扱う（レポートで限界として述べる）。
